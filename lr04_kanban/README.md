## 1. Definition of Workflow

| Колонка | Картка потрапляє сюди, коли | Картка виходить звідси, коли |
| --- | --- | --- |
| Backlog | Створено конкретну роботу на один-два дні з ключем F-0NN і типом; її ще не підготовлено до виконання. | Сформульовано перевірюваний результат, обсяг роботи та відомі залежності — тоді в Ready. |
| Ready | Є зрозумілий критерій завершення, завдання можна взяти без додаткового уточнення й виконати орієнтовно за один-два дні. | Фактично почалась робота над результатом, записано дату старту й є місце за WIP-лімітом — тоді в In progress. |
| In progress | Виконавець реально працює над карткою; дату старту зафіксовано. Зовнішній блокер не маскується іншим статусом: картка лишається тут, а дні блокування рахуються окремо. | Є доступний для перевірки результат (файл, коміт або чітко зафіксоване рішення) — тоді в In review. |
| In review | Результат можна відкрити та звірити з критерієм завершення; посилання або файл доступні для перевірки. | Результат відповідає критерію — тоді в Done; якщо знайдено недолік, повертається в In progress з описом доробки. |
| Done | Результат перевірено, критерій завершення виконано й записано фактичну дату завершення. | Не виходить; нову роботу або дефект оформлюємо окремою карткою. |

Назва колонки на дошці — In review; у каркасі умови це Review, зміст однаковий. Переміщення картки означає подію, а не бажаний вигляд дошки.

## 2. WIP-ліміти

| Колонка | Ліміт | Чому саме такий |
| --- | :-: | --- |
| In progress | 2 (було 3) | Початковий ліміт 3 зменшено на одиницю за конвертом 1; вплив ще не оцінено. |
| In review | 2 | Якщо перевірка накопичується, спочатку завершуємо вже підготовлені результати, а не додаємо нові. |

Ліміти встановлені на самій дошці. Коли ліміт вичерпано, нову картку не починаю: перевіряю або закриваю поточну, а нова чекає в Ready. Якщо зовнішній блокер зупиняє картку в роботі, фіксую його дату й дні, не називаючи її завершеною.

Коли ліміт спрацював: поки не зафіксовано.

Таблицю в цьому README синхронізувати з дошкою того самого дня. Не потрібно щодня пересувати по одній картці: можна зробити кілька, поки не порушено WIP-ліміт і статуси відображають факти.

## 5. Конверт 2, термінова картка

Тригер настав 2026-10-09 після п'ятої Done, F-006. Це **обов'язковий навчальний уявний збій**: справний валідатор не скасовує вправу. Виконано 2026-10-11 карткою [F-013, Issue №32](https://github.com/100kgtrotila/it-project-management/issues/32), із запізненням щодо тригера. Уявний дедлайн «через два дні» не є фактичним дедлайном пакета.

Стан перед виконанням вправи 2026-10-11, до створення F-013: Backlog 5 (F-008–F-012), Ready 0, In progress 1 (F-001), In review 0, Done 6. Історичний стан перед п'ятою Done 2026-10-09: Backlog 6, Ready 1, In progress 1, In review 0, Done 4. Ці два моменти не підміняють один одного.

Що зупинено для термінової картки: активну F-001 не зупиняли, бо був один вільний слот. Фінальне оформлення F-008–F-012 почекало завершення expedite. Під час вправи In progress = 2/2, у Review — одна F-013; жодного ліміту не перевищено. Перехід F-013: Backlog → Ready → In progress → In review → Done.

Відтворення й виправлення: у тимчасовій копії `lr01_case/sources.csv` дата `accessed=2026-10-40` спричинила одну помилку `date`, рядок 2, exit 1. Відновлення `2026-09-19` дало 0 помилок і 0 попереджень, exit 0. Оригінальна папка ЛР1 не змінена (`git diff -- lr01_case` порожній).

Час поява → завершення F-013: **1 хв 36 с**, від 2026-10-11 23:18:07 до 23:19:43 за Києвом; джерело — `created_at` і `closed_at` Issue №32. Це фактичний час навчальної вправи, не час реального інциденту.

Якщо expedite буде три на тиждень, звичайні картки частіше чекатимуть і прогноз стане менш надійним. Пропоную окрему позначку expedite з лімітом одна активна картка в межах загального WIP; другий і третій запити за тиждень брати лише після узгодження з PM, яка звичайна робота переноситься. Повторні помилки попереджати запуском валідатора до переходу в Review. Це правило для гіпотетичної ситуації, не виміряний наслідок.
